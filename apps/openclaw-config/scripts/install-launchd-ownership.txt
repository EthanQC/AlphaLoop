# Single source of truth for "which launchd domain owns which label".
#
# Task 9 (2026-07-28 spec-drift remediation): the unattended services used to
# be installed as USER-level LaunchAgents under ~/Library/LaunchAgents. A
# LaunchAgent is only bootstrapped once a GUI login session for that user
# exists, so a reboot that stops at the login window (a panic, a power cut, a
# `sudo reboot` over ssh) left platform-app / cron-runner / market-alerts /
# daily-backup / official-paper poll+pnl DOWN until a human physically logged
# in. The "重启自愈" property the project claims was therefore not real.
# Those labels now live in /Library/LaunchDaemons with an explicit UserName,
# which launchd bootstraps at boot with no session at all.
#
# Format: "<scope> <label>", one per line, "#" starts a comment.
#
#   system    installed by install-system-daemons.sh into /Library/LaunchDaemons
#             (needs sudo). No other installer may write this label anywhere.
#   user      installed by install-launchd.sh into ~/Library/LaunchAgents.
#             Only for jobs that genuinely need the user's login session.
#   retired   must never be installed by anyone; the installers boot it out and
#             move any leftover plist into the backup directory.
#   external  owned by a third-party installer (the `openclaw` CLI), not by
#             anything in this repo. Listed only so install-launchd.sh knows to
#             leave the checked-in template alone instead of treating an
#             unlisted label as a mistake.
#
# Every consumer reads THIS file rather than keeping its own copy, so a label
# has exactly one owner by construction:
#   - install-system-daemons.sh  aborts unless the set of daemons it renders
#     equals the "system" rows here, and retires every "system"/"retired"
#     label from ~/Library/LaunchAgents before bootstrapping the daemons.
#   - install-launchd.sh         installs a template only when its label is
#     scoped "user"; an unlisted template is a hard error, never a silent skip.
#   - install-user-schedules.mjs / install-openclaw-cron.mjs no longer install
#     any plist; they only retire "system"/"retired" labels, so re-running them
#     in any order can never resurrect a user-level copy of a system daemon.
#
# Labels that are NOT ours (the mini also runs the operator's personal
# 185-agent OpenClaw: com.qingverse.*, com.xhs.*, com.kb.*, pm2.*,
# homebrew.mxcl.*, com.google.*, com.microsoft.*) must never appear here and
# are never touched by any of these installers.

system   ai.openclaw.system.gateway
system   com.openclaw.system.trading.broker-executor
system   com.alphaloop.platform-app
system   com.alphaloop.memoryd
system   com.alphaloop.market-alerts
system   com.alphaloop.daily-backup
system   com.openclaw.trading.cron-runner
system   com.openclaw.trading.official-paper.poll
system   com.openclaw.trading.official-paper.pnl
# RSSHub must recover before a GUI login after a cold reboot. The daemon runs
# as the operator (not root), explicitly starts that user's Colima runtime,
# then starts the pre-created loopback-only container. `colima start` is
# idempotent; a missing runtime or container deliberately makes the one-shot
# job fail and leaves the error in logs/rsshub.err.log.
system   com.alphaloop.rsshub

# Superseded by com.openclaw.system.trading.broker-executor above. Kept here
# (rather than deleted) so every installer keeps actively booting it out: a
# machine that ran an older checkout still has the user-level copy on disk,
# and two broker-executors racing on the same trading database is exactly the
# failure this manifest exists to prevent.
retired  com.openclaw.trading.broker-executor

# The live gateway is ai.openclaw.system.gateway, installed only by
# install-system-daemons.sh. These external rows describe historical or
# third-party labels that our user-level installer must never render.
# install-system-daemons.sh still boots out a legacy ai.openclaw.gateway during
# migration, but install-launchd.sh no longer recreates it. That is required
# for headless cold-boot deployments, where gui/<uid> does not exist.
external ai.openclaw.gateway
external com.openclaw.gateway

# The public entry point. Listed because "which installer owns this label" was
# genuinely ambiguous until 2026-07-28 and the wrong answer stands up a second
# tunnel connector next to the live one.
#
# Read-only measurement on the mini, 2026-07-28:
#   /Library/LaunchDaemons/com.cloudflare.cloudflared.plist  root:wheel, Jul 27
#   launchctl print system/com.cloudflare.cloudflared        state = running
#   argv: /opt/homebrew/bin/cloudflared --config /etc/cloudflared/config.yml
#         tunnel run          (named tunnel; credentials in root-only
#         /etc/cloudflared/<tunnel-uuid>.json, mode 600)
#   https://reports.qingverse.com/health -> HTTP/2 200 via Cloudflare anycast
#   (104.21.27.3 / 172.67.139.197, cf-cache-status header present)
#
# That daemon is installed by `cloudflared service install`, NOT by this repo,
# so its scope is "external" - nothing here writes or removes it. It also wins
# on the exact axis this manifest exists for: it is a system daemon, so it
# comes back after a reboot with no GUI login, which is why the ten labels
# above were moved out of ~/Library/LaunchAgents in the first place.
#
# install-cloudflared-tunnel.mjs installs a DIFFERENT label
# (com.alphaloop.cloudflared-tunnel, a user LaunchAgent running the token
# form `cloudflared tunnel run --token ...`). Because the labels differ,
# launchd would happily run both, and the repo installer would add a second
# connector alongside the live one. It therefore refuses to install when
# com.cloudflare.cloudflared is present, unless run with --force. Its own
# label is deliberately NOT listed here: on a machine with the system daemon
# it must never be installed, and a machine without one is a fresh install
# where the operator picks a path explicitly.
external com.cloudflare.cloudflared
